## Goal

Demonstrate the smallest convincing version of Rehabify's core product loop:

```text
interactive patient voice intake
  -> source-linked clinician brief
  -> clinician assessment
  -> deterministic constrained plan draft
  -> clinician approval
  -> patient-visible Today plan
```

The demo should prove that Rehabify converts patient context into a useful
clinician-controlled rehabilitation plan. It should not attempt to demonstrate
the entire production architecture or real-patient readiness.

## Locked Decisions

- Build one unified Next.js `/demo` experience.
- Present from a laptop browser.
- Show clinician screens at desktop width.
- Show the final patient Today experience inside a phone frame.
- Reuse the existing interactive voice-intake work.
- The intake completes automatically after its final required answer.
- Do not make transcript review a separate demo beat.
- Automatically hand off from completed intake to the clinician brief.
- Use discreet manual presenter controls after the intake handoff.
- Run the existing deterministic plan composer in memory.
- Enhance the presentation around the composer rather than redesigning its
  rule engine.
- Show one unsuitable exercise being rejected with a plain-English rule reason.
- Require explicit clinician approval before the plan becomes patient-visible.
- End the demo on the patient's Today plan.
- Polish the existing calm clinical visual direction rather than redesigning
  the product or creating a theatrical showcase theme.
- Keep Postgres, external speech providers, and external model calls off the
  critical live-demo path.

## Three-Minute Narrative

| Time | Scene | Presenter outcome |
| ---: | --- | --- |
| 0:00-0:10 | Product setup | Explain that patients describe their condition before the appointment and clinicians receive structured, source-linked context. |
| 0:10-0:40 | Interactive voice intake | Answer the patient intake by voice. The intake visibly progresses and completes automatically. |
| 0:40-0:48 | Handoff | Show a short `Preparing your clinician summary...` transition, then move automatically into the clinician workspace. |
| 0:48-1:20 | Clinician brief | Show the patient story, one explicitly missing fact, and source evidence. Do not spend time reading a raw transcript. |
| 1:20-1:45 | Assessment | Show the clinician's prefilled structured assessment and the minimum interaction needed to make it plan-ready. |
| 1:45-2:25 | Plan composition | Run the deterministic composer, show rule evaluation, reject one unsuitable exercise, and reveal the eligible plan. |
| 2:25-2:42 | Approval | Make the clinician approval boundary visible. No plan becomes patient-visible before approval. |
| 2:42-2:55 | Patient Today | Transition into a phone frame showing the approved plan and the patient's next action. |
| 2:55-3:00 | Close | State that Rehabify turns patient context into a clinician-controlled rehab plan before and between visits. |

The timings are targets, not automatic timers. Presenter-controlled navigation
after intake allows the speaker to recover if any scene runs long.

## Demo Story

Use one deterministic synthetic adult knee-rehabilitation case throughout.
Reuse the existing Maya/right-knee scenario where practical so that current
prototype content, source-linked brief facts, assessment values, plan items,
and Today content remain consistent.

The story must have:

- a clear patient goal;
- a plausible symptom and activity history;
- one missing or unanswered fact that remains visibly unknown;
- structured clinician findings;
- at least one valid exercise;
- one deliberately unsuitable exercise rejected by deterministic rules;
- a clinician-approved final plan; and
- a clear patient next action.

No scene may imply diagnosis, autonomous prescribing, clinical readiness, or
real-patient use.

## Experience Architecture

The demo should be one client-side state machine with a stable fixture:

```text
patient_intake
  -> preparing_brief
  -> brief_review
  -> assessment
  -> composing_plan
  -> plan_review
  -> approved
  -> patient_today
```

Each transition should be explicit and deterministic. Refreshing the page
should return to a known start state or restore a deliberately persisted
demo-only scene marker. It must never depend on production authentication,
provider availability, background jobs, or mutable shared demo data.

### Navigation behavior

- Intake advances according to its existing interaction model.
- The final required intake answer triggers automatic completion.
- Completion shows a short preparation state before opening the brief.
- Brief, assessment, plan review, and Today use presenter-only `Previous` and
  `Next` controls.
- Presenter controls should be visually quiet and separated from product
  controls so the audience does not confuse them with application features.
- A reset control returns the entire demo to the first intake scene.
- Direct scene selection may exist behind a presenter menu for rehearsal and
  recovery, but should not be visible in the normal narrative.

## Scene Requirements

### 1. Interactive voice intake

Reuse the existing browser voice-capture controller and its working behavior:

- microphone permission handling;
- listening state and input-level feedback;
- explicit stop and cancel actions;
- bounded recording duration and size;
- text fallback;
- safe recovery from unsupported or denied microphone access; and
- memory-only audio handling.

For the demo path, voice interaction must advance the deterministic intake.
The live path does not need a production STT provider. The implementation may
map a successful recording turn to the next fixture answer, provided the demo
is visibly labelled synthetic and the interaction itself remains real.

The demo should not stop to show or edit a transcript. The source-linked brief
is the payoff.

### 2. Clinician brief

Reuse the content and visual hierarchy from the existing prototype and
production-shaped brief workspace:

- patient story first;
- symptoms and behavior;
- goals;
- one missing or unknown answer;
- source affordances for material facts; and
- a clear review state.

Source inspection should reveal concise evidence rather than opening a long
raw transcript. The presenter needs one fast interaction that proves
provenance.

### 3. Assessment

Use a concise, prefilled knee assessment. The presenter should make at most one
meaningful edit or confirmation before advancing.

The screen must distinguish:

- patient-reported context;
- clinician-recorded findings;
- missing/not-tested values; and
- the clinician's working hypothesis.

Do not reproduce the full production assessment workflow in the demo.

### 4. Deterministic plan composition

Run the existing deterministic composer in memory with a stable synthetic
fixture. The visible generation sequence should be short:

1. Read the verified brief and assessment inputs.
2. Check clinic-approved content and dosage limits.
3. Evaluate eligibility rules.
4. Move one unsuitable exercise into a rejected panel.
5. Show the eligible proposed plan.

The rejected candidate must show a human-readable reason, such as a missing
prerequisite, incompatible assessment finding, equipment constraint, or
validated dosage/eligibility rule. The rejection should be a product moment,
not a developer trace dump.

The eligible result should contain a small plan, ideally three exercises, with
clear dosage and rationale.

### 5. Clinician approval

The plan begins as a draft. The clinician must approve it before the patient
view can open.

The demo should make these boundaries clear without turning the scene into a
compliance lecture:

- Rehabify drafts.
- Deterministic rules constrain.
- The clinician decides.
- Only the approved plan becomes patient-visible.

Treatment-consent mechanics may be represented as already satisfied by the
synthetic fixture unless the approval interaction can include them without
slowing the story.

### 6. Patient Today

End in a phone frame showing:

- the patient greeting and current week;
- the next approved exercise;
- simple dosage;
- one clear primary action;
- weekly context; and
- the next review date.

This final screen should feel like the direct outcome of the clinician's
approval rather than a disconnected prototype.

## Visual Direction

Polish the existing calm clinical utility style:

The cross-cutting, screen-by-screen implementation details and P0/P1/P2 cut
line are captured in
`docs/specs/2026-07-27-yc-demo-ui-improvements.md`.

- restrained light surfaces;
- high-contrast readable type;
- consistent spacing and card geometry;
- one clear primary action per scene;
- explicit state labels;
- limited clinical-status color;
- subtle transitions between scenes; and
- reduced-motion support.

The clinician workspace should feel dense but calm. The patient phone frame
should feel simpler and warmer. Avoid dramatic gradients, excessive motion,
glowing AI effects, chat-style novelty, or a generic dashboard aesthetic.

Polish priority:

1. Voice intake
2. Clinician brief
3. Plan composition and approval
4. Patient Today
5. Assessment
6. Presenter controls

## Explicit Non-Goals

Do not spend the demo sprint on:

- production STT or TTS provider integration;
- production model integration;
- real authentication or OTP delivery;
- a complete Postgres domain seed;
- background job orchestration;
- real-patient data;
- clinical-content approval;
- full assessment persistence;
- full plan correction history;
- treatment-consent workflow expansion;
- check-ins, holds, attention triage, or follow-up screens in the live
  three-minute path;
- broad responsive support beyond the presentation viewport and Today phone
  frame;
- infrastructure, deployment architecture, or multi-tenant hardening;
- redesigning the deterministic plan composer;
- redesigning the product's visual language; or
- cleaning unrelated repository files as part of demo implementation.

The broader loop remains valuable product evidence, but it is outside this
three-minute demo's live path.

## Implementation Sequence

### Phase 1: Demo shell and fixture

- Add the unified `/demo` route.
- Define the complete synthetic case in one typed fixture.
- Define the demo state machine and presenter navigation.
- Add deterministic reset and direct-scene recovery.
- Establish clinician desktop and patient phone-frame shells.

### Phase 2: Intake and handoff

- Integrate the existing browser voice-capture controller.
- Connect successful voice turns to deterministic intake progress.
- Automatically complete the intake after the final required answer.
- Add the brief-preparation transition.
- Verify microphone denial and text fallback do not block the demo.

### Phase 3: Brief and assessment

- Adapt the strongest existing brief hierarchy to the demo fixture.
- Add one source-inspection interaction and one explicit missing fact.
- Add the concise prefilled assessment.
- Make the brief-to-assessment and assessment-to-plan transitions presenter
  controlled.

### Phase 4: Composer and approval

- Build the in-memory composer adapter around the existing deterministic
  composer.
- Create stable eligible and rejected candidates.
- Add the visible rule-check sequence and plain-English rejection reason.
- Render the final proposed plan.
- Require clinician approval before enabling Today.

### Phase 5: Today and polish

- Render the approved plan in the patient phone frame.
- Ensure the final state visibly derives from the approved draft.
- Polish the five live scenes and transitions.
- Add reduced-motion behavior.
- Rehearse the complete path against the three-minute script.

### Phase 6: Verification

- Add reducer tests for every allowed scene transition.
- Add a voice-success test that completes intake and opens the brief.
- Add a text-fallback test that reaches the same state.
- Add composer tests for eligible and rejected candidates.
- Add an approval gate test proving Today is unreachable before approval.
- Add reset/recovery tests.
- Run focused typecheck, unit tests, and a production build.
- Run the demo repeatedly with microphone permission allowed and denied.
- Perform at least five timed rehearsals; target a normal completion under
  2:45 to preserve recovery margin.

## Definition of Done

The YC demo is ready when:

- it begins from a single stable URL;
- a real microphone interaction advances the synthetic intake;
- the intake completes automatically;
- the brief clearly shows value and source provenance;
- the assessment-to-plan transition is understandable;
- the deterministic composer runs without external dependencies;
- one unsuitable exercise is visibly rejected by a rule;
- a valid draft is displayed with clear rationale and dosage;
- the patient Today screen cannot be reached before clinician approval;
- the final Today screen reflects the approved plan;
- presenter controls allow recovery without exposing implementation details;
- the complete presentation runs reliably five times in a row;
- the normal presentation finishes in under 2:45;
- microphone denial has a rehearsed text-fallback path; and
- no real patient data, production provider, or clinical-readiness claim enters
  the demo.

## Risks

| Risk | Mitigation |
| --- | --- |
| Voice permission fails during presentation | Rehearse browser permissions and keep the existing complete text fallback. |
| Voice interaction consumes too much time | Keep the normal path to two or three short explicit push-to-talk turns; use text fallback or presenter recovery rather than silently completing unperformed turns. |
| Composer output changes unexpectedly | Use one immutable fixture and deterministic evaluator pins. |
| Audience mistakes the demo for autonomous prescribing | Keep clinician approval visually central and use precise presenter language. |
| Demo looks like disconnected prototypes | Use one state machine, one patient identity, consistent data, and animated scene continuity. |
| Styling consumes the sprint | Reuse the existing prototype design and polish only the live path. |
| Presenter loses their place | Add quiet Previous, Next, Reset, and recovery scene controls. |
| Dirty working tree contaminates the change | Stage explicit files only and keep duplicate untracked files outside scope. |

## Resolved Review Items

- A successful real browser recording advances the current deterministic
  fixture answer. The route and presenter language explicitly say the case
  mapping is synthetic; no transcript or speech-understanding claim is shown.
- Treatment consent is outside the live path. Explicit clinician approval is
  the visible human gate.
- The rejected exercise uses the real composer code
  `not_included_by_playbook`, translated into plain-English clinic-rule copy.
- Opening the bounded source excerpt marks the brief reviewed; presenter Next
  performs navigation.
- The assessment requires one edit from `4/10` to `3/10` and one explicit
  confirmation.
- The static prototype is a visual reference only. `/demo` ports a small
  token/layout subset into scoped CSS modules.
- Same-tab recovery stores only a stable scene marker. Restored approval/Today
  scenes normalize to plan review and require a fresh exact approval.
- Validation begins with exact focused test paths. Any repeated stall is
  captured with the command, duration, and last output before a single-file
  timeout investigation.
